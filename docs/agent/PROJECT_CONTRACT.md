# Project Contract

## Product outcome

Project Workbench is an external DeepSeek Harness Cordis plugin. It will provide a project-centered workspace for durable project state, documents, collaboration, and AI-native progress/risk/topic workflows. T01 established the durable Host-to-browser walking skeleton, T02 added the local Owner boundary, T03 completed the traceable transaction/Outbox/audit seam plus Owner Activity, T04 added immutable Template-driven Project creation, T05 added the Project-scoped roster and responsibility tuple, T06 added evidence-backed review, T07 added explicit Feishu Bot/User identity continuity, T08 federated one primary Feishu Task List, T09 mapped a Project workflow to one Feishu custom field, and T10 bound an authoritative Feishu calendar with Milestones. The current implementation boundary is GitHub Issue #12 (T11): create one immutable Deliverable plan, link its responsibilities, authoritative calendar event, execution tasks, and declared artifact versions, then carry one typed acceptance request through Review Center to an immutable Final Release.

## Runtime shape

- `@benz-ai-x/dsh-project-workbench` owns Host truth, the `workbench` Typert Remote namespace, SQLite persistence, the injectable `WorkbenchScenario` test seam, and the Owner authentication/authorization boundary.
- `@benz-ai-x/dsh-project-workbench-client` owns the browser projection and UI. It mounts the generated Remote artifact before registering into the `conversation` Slot and tears down in reverse order.
- `@benz-ai-x/dsh-project-workbench-bundle` inserts the Host and Client rows. The tracked `workbench-test` profile composes `dsh-base`, `dsh-web-app`, and this bundle.
- Host state never crosses through a custom Session event. Client code never imports Node, repository, credentials, or external adapter implementations.
- The neutral status remains the first formal command target; T04–T11 extend the same ledger rather than creating parallel authority paths.

## Invariants

- Host Service packages use the Service plugin shape: explicit static injection, static Config, generated Typert artifacts, and a default Service export. Namespace function plugins use named exports and no accidental default export.
- Public `Config` has a TypeScript interface and a same-named Schemastery runtime schema. Defaults live in the schema. Invalid values fail through the real Loader path.
- Public commands validate before commit. Observers receive only committed whole-value projections. Revision conflicts are explicit and never silently overwrite another writer.
- `WorkbenchScenario` accepts a deterministic clock, ID generator, Repository, and external adapter set. Its public command/query seam is the primary test boundary.
- Disposal closes admission, waits for accepted work, removes Client Slot and Remote contributions, then closes owned persistence. No timer, listener, Remote, database handle, or late async publication may survive its Fiber.
- Client state distinguishes loading, ready-empty, ready-value, pending, stale/disconnected, domain conflict, and transport failure. It keeps the last authoritative value while stale, preserves recoverable drafts, prevents duplicate submission, uses typed zh/en copy, and is keyboard/screen-reader usable.
- UI code registers in a declared additive/replacement Slot and never registers `root`. It uses CSS Modules and Harness semantic theme tokens; no global CSS, hard-coded theme colors, or new component framework.
- External DSH packages stay source-linked until a clean registry-install closure is proven. Passing local checks is not a publication-readiness claim.

## T02 identity and transport invariants

- V1 has exactly one local Owner. Initialization is an atomic absent-to-present DSH credential-record transition; a second initializer never creates another login identity.
- The DSH Connection launch cookie remains an outer Harness-access fence, not the Workbench login. Workbench owns a separate `__Host-` session cookie with `Secure`, `HttpOnly`, `SameSite=Strict`, `Path=/`, and no `Domain` attribute.
- Password verification uses Argon2id. Raw passwords, recovery codes, and session tokens are ephemeral; only a PHC password hash and high-entropy token digests may enter the versioned `project-workbench/owner-auth` DSH credential record.
- The Workbench `/api/workbench` carrier route first reuses Connection's Host/Origin/launch-cookie rejection, then authenticates the Owner session, removes the opaque Owner cookie from the internally forwarded request, and establishes a Host-only principal context before forwarding to the generated Typert Gateway handler.
- Every public Workbench scenario command/query independently calls the same `AuthorizationPolicy` seam. Missing principal context denies access, including direct in-process invocation; the carrier check is defense in depth, not the sole policy call.
- The Client treats the server-issued absolute session deadline as a fail-closed projection fence: a deadline timer, window reactivation, and every protected local/Remote operation erase cached status, drafts, and recovery plaintext once expired. Host session validation remains authoritative on every request.
- Logout removes the server-side session before clearing the browser cookie. Password recovery consumes the current code, increments the credential version, invalidates every session, and issues one replacement code exactly once.
- Recovery is a local package CLI with hidden TTY input (and a bounded stdin mode for automation), not a public browser form. It uses the official DSH credential provider rather than parsing its backing file.
- T02 deliberately did not invent a competing authentication audit store. T03's atomicity claim applies to formal business commands in the Workbench SQLite database. Owner credentials live in the separate DSH credential provider, so authentication/recovery mutations and this ledger cannot honestly be described as one atomic transaction; durable security-event integration requires an explicit later cross-store design rather than a best-effort optional sink.

## T03 command, Outbox, and audit invariants

- Every formal mutation carries a caller-stable idempotency key, causation ID, bounded reason code, expected version, and a server-derived authenticated actor. Browser input never supplies actor or organization scope.
- The normalized business mutation, one immutable pending Outbox intent, one append-only audit event/hash-head advance, and the replay receipt live in the same SQLite file and one synchronous `BEGIN IMMEDIATE` transaction. No `await`, adapter call, observer, or log call occurs while that write transaction is held.
- Receipt lookup precedes optimistic-concurrency validation. The same actor/key and same normalized intent returns its stored result without another mutation, event, or Outbox row; reuse for different intent is an explicit domain conflict.
- A committed audit event contains only allowlisted fields: actor, organization/team scope, bounded reason, action, nullable Project scope, object identity/version, command ID, causation ID, Outbox ID, timestamp, and safe summary code. Status text, credentials, tokens, request bodies, headers, raw errors, and arbitrary metadata never enter audit or Activity.
- Audit hashes use a versioned RFC 8785-compatible canonical JSON envelope and SHA-256 with sequence and previous hash. Verification recomputes the complete chain and compares the stored head. This is tamper evidence, not non-repudiation against an attacker able to rewrite the database and every external checkpoint.
- Outbox states are facts: `pending`, `delivered`, `unknown`, and `failed`. A transport outcome that may have taken effect is `unknown`, never blindly retried with a fresh effect key or aged into `failed`.
- Activity and audit-integrity reads authorize before storage, constrain organization from the Host principal, apply Project/object/action filters in the repository, and return only detached browser-safe projections.

## T04 Project Template, Goal, Outcome, and Project invariants

- The canonical domain vocabulary is recorded in `CONTEXT.md`. A Project has exactly one Primary Goal and zero or more distinct Supporting Goals; a Goal owns at least one Outcome, and an Outcome is a measurable result rather than a task or output.
- The built-in Knowledge Work Template is one immutable Template Version with a closed runtime schema, canonical bytes, and a SHA-256 digest. A changed definition must be a new Template Version; no caller may select a mutable `latest` alias.
- Every Project records Template Version provenance and owns a complete immutable Project Template Snapshot. The creation snapshot is copied, digest-verified, and never rewritten by a future Template Version or upgrade.
- Project creation is one formal command: catalog CAS, Supporting Goal revision/scope checks, Primary Goal, ordered Outcomes, Project, snapshot, links, pending Outbox, one Project-scoped audit event/hash-head advance, and replay receipt either commit together or do not exist.
- Outcome metrics carry bounded names, a finite baseline and target, a bounded unit, and an increase/decrease direction consistent with those values. Execution completion and Outcome attainment remain separate concepts.
- The browser supplies exact Template Version/digest, expected revisions, idempotency key, causation ID, and bounded domain input. Actor, organization/team scope, generated IDs, time, audit vocabulary, and Outbox facts remain Host-derived.
- Project names, Goal/Outcome text, metric values, Template Snapshot content, request bodies, and raw failures never enter audit or Activity. The Project detail projection may return authorized business values as detached whole objects.

## T05 ProjectMember and responsibility invariants

- A ProjectMember is a stable, Project-scoped responsibility identity, not a Workbench login, Feishu contact record, or runnable Agent Profile. T05 admits exactly one creation identity variant: declared Feishu human (`appId + openId`), external-contact human, or descriptive Agent.
- A declared Feishu identity is app-scoped metadata, not verified connector truth. Only an active declared-Feishu human is marked as having an assignee identifier; T07 must verify connection scope and T08 remains authoritative for real Feishu task assignment.
- The Project is T05's only Responsibility Target. Its current Project Responsibility is either unconfigured or one complete tuple with exactly one active Accountable, zero or more distinct active Contributors excluding the Accountable, and a Human Sponsor when the Accountable is an Agent or external-contact human.
- Human Sponsor is an active human ProjectMember distinct from the sponsored Accountable. Sponsor is oversight and escalation, not a second Accountable, and may also be a Contributor.
- Project Team revision serializes roster creation, member status, and responsibility replacement. Responsibility versions are append-only. ProjectMember status is reversible; identity rows are never deleted, and a current Accountable, Contributor, or Sponsor must be reassigned before deactivation.
- Member creation, status change, and responsibility replacement are authorized T03 commands with receipt-first replay, exact CAS, one pending Outbox fact, one Project-scoped audit event, and one receipt in the same transaction. Success receipts contain only IDs, versions, safe status/kind codes, and correlation IDs.
- Display names, Feishu app/open IDs, external-contact values, complete responsibility input, raw request/failure content, and Project Team projections never enter audit, Activity, Outbox payloads, diagnostics, or immutable command receipts. Authorized roster reads may return detached business values.
- The live Client controller retains Team drafts and exact retry identity across recoverable conflicts and connection-generation resets. Project switch, logout, session expiry, and Fiber disposal erase them. Under the pinned DSH HMR contract, a replacement Fiber re-reads Host truth after the Owner explicitly reopens the Project; T05 does not place protected draft data in Web Storage or a process-global handoff.

## T06 Review Center and SuggestedChange invariants

- T06 exposes exactly three new behaviors: one Project-scoped Review Center query, one typed Project Responsibility proposal command, and one closed accept/edit-and-accept/reject/defer decision command. It does not expose a generic patch endpoint or a runtime-extensible adapter registry.
- T06 uses stable Host policy capabilities: `workbench.review.read` for the Review projection and `workbench.review.decide` for proposal/decision commands. Accept and edit-and-accept additionally require `workbench.project.responsibility.write`; both grants must resolve to the identical Owner/organization/team scope before persistence begins. No authorization callback or other `await` runs inside the SQLite transaction.
- A SuggestedChange is an immutable Owner-sourced proposal envelope plus a small mutable CAS head and append-only Review Decisions. Source actor, organization/team scope, IDs, timestamps, typed Review Diff, digest, risk, policy reasons, and batch policy are Host-derived.
- The only T06 Review Target is `project-responsibility.replace`. The browser submits a complete semantic candidate, exact Project Team revision, 1–20 distinct immutable same-Project audit-event EvidenceRefs (canonically ordered by audit-event ID), idempotency key, causation ID, and closed reason. It cannot submit source, target identity, actor/scope, before value, diff, digest, risk, or committed versions.
- The Host normalizes Project Responsibility as a complete tuple, treats Contributors as a canonical set, and derives a versioned typed before/after/changed-fields Review Diff. The stored diff is for review and integrity; execution always decodes the typed candidate and reuses the same transaction-local Responsibility invariant planner as the direct T05 command.
- Proposal risk is `high` for initial configuration or an Accountable/Human Sponsor change and `low` only when those roles are unchanged and the Contributor set changes. The policy version and reason codes are retained. Both levels require individual confirmation in T06; only actionable low-risk items expose a non-operational homogeneous-batch eligibility seam.
- `pending`, `deferred`, `accepted`, and `rejected` are persisted states. `stale` is an effective Host projection for unresolved items whose current Team revision differs from the immutable base. Accept, edited accept, and defer cannot change or replace that base; a stale item may only be rejected, and renewed intent requires a new proposal.
- Every decision requires bounded feedback. Edited accept retains the original candidate/diff and appends a separately derived applied candidate/diff. Its effective risk is the higher of proposed and applied risk, so editing cannot downgrade the reviewed policy.
- Accept and edited accept reauthorize both review and target write authority, perform receipt-first replay, CAS the SuggestedChange revision and immutable Team base, re-resolve evidence, rerun current member/role/Sponsor invariants, and atomically append the Responsibility version, Review Decision, Review head, one redacted Outbox intent, one hash-chained audit event, and one immutable receipt.
- Reject and defer are also formal T03 commands with receipt-first replay, Review CAS, one append-only decision, redacted Outbox/audit, and one receipt, but never mutate the target. `accepted` means the target mutation committed in that same transaction, not merely that work was queued.
- Full proposal candidates, before/after member IDs, EvidenceRef contents, and Owner feedback remain in authorized Review storage/projections. They never enter Activity, generic audit fields, Outbox payloads, receipts, logs, diagnostics, or raw error messages.
- The Review Client distinguishes a domain item's effective `stale` status from a disconnected transport projection, prevents duplicate decisions, retains only exact ambiguous-transport retry envelopes, and never auto-submits after refresh. Project switch, logout, expiry, HMR/Fiber disposal, and selection clearing erase protected drafts; reopening reads Host truth.

## T07 Feishu Connection Center invariants

- One workspace-scoped Feishu Connection owns independent `bot` and `user` Identity Routes. Every provider operation receives exactly one route; a scope, authorization, credential, or ACL failure never retries through the other actor.
- Route configuration persists only `appId` and a DSH `CredentialRef`. Secret and token values are resolved once per external operation, remain in the smallest Host lexical scope, and never enter SQLite, Remote projections, audit, Activity, Outbox, receipts, logs, or browser state.
- Configuration, reset, and disable create append-only route generations under connection and route CAS. Ordinary configuration edits and disable/re-enable preserve a separate identity-continuity epoch; reset alone advances that epoch and is the only intentional way to clear its binding. Disable never promotes the other route to fallback.
- The first successful verification of a continuity epoch creates one immutable Actor Binding with its original route-generation provenance. A later `appId/openId/tenantKey` mismatch is an append-only failed verification with closed recovery guidance and cannot overwrite the binding.
- Bot verification exchanges the exact route's App Secret for an ephemeral tenant token and calls Bot self-info. User verification calls User self-info with the exact configured User token. Neither self endpoint is represented as proof of Task, Calendar, Docs, tenant-wide, or resource authorization.
- Existing Actor Binding continuity is checked after self-info and before any optional resource request, then enforced again at the durable commit boundary. Optional Task-list diagnostics use the same one-shot actor session and are read-only. Missing app scope, missing User grant, resource ACL denial, and resource-not-found remain different closed facts and recovery paths; unknown effective scope remains honestly unknown and an unrecognized User 403 is never guessed to be authorization revocation.
- Provider network reads occur outside SQLite write transactions. Receipt replay is checked before any provider call; the safe observation, connection revision, one pending Outbox fact, hash-chained audit event, and immutable receipt commit atomically afterward.
- The authorized settings projection may show `appId`, credential-reference presence metadata, bound `openId/tenantKey`, safe scope facts, resource ID, and the latest verification. Generic audit/Activity/Outbox surfaces remain credential-, identity-, and resource-ID-free.
- The Client keeps Bot/User forms and results separate, retains only exact response-loss retry identity, preserves drafts across same-Owner reconnect, and erases protected values on logout, expiry, Owner change, and Fiber disposal.

## T08 Feishu Task federation invariants

- A Project has zero or one immutable primary Feishu Task List binding. Binding either selects an accessible list or creates one with Feishu's `client_token`; it pins the exact verified Bot/User route generation and never falls back to the other identity. A task-list GUID cannot silently become another Project's primary binding.
- Feishu is authoritative for task title, description, parent/subtask relation, assignees, followers, comments, completion state, canonical URL, and opaque remote version. Workbench stores a bounded, detached local projection for availability and analysis; it does not claim to own those fields independently.
- A complete reconciliation replaces the primary-list subset from one bounded remote baseline while preserving explicitly referenced outside-list tasks. Every attempt records healthy/attention state and advances a Project task revision under CAS. A periodic Host timer is repair, not the sole correctness path, and is cancelled during Scenario disposal.
- Trusted Host adapter events are normalized before persistence. The append-only Inbox deduplicates event IDs; opaque remote versions reject stale/out-of-order observations; unknown list bindings are ignored. Missing events converge through the periodic complete reconciliation. Event ingestion is an internal Scenario seam and is never exposed as a browser Remote.
- Tasks outside the primary list are invisible by default. Only the Owner-authorized, audited explicit-reference command may add one to Project scope. Reconciliation and removal events retain that reference until a later ticket defines an explicit removal policy.
- Every Workbench-originated task update carries the current Project task revision, the task's opaque Feishu remote version, one caller-stable idempotency key, one causation ID, and a closed reason. The Host durably reserves and claims the effect before exactly one provider PATCH attempt.
- Task update replay is receipt-first. `prepared` may be claimed once; a recovered `inflight` effect becomes durably `unknown` and is never offered for delivery again. Confirmed success updates the projection; a remote-version conflict projects current Feishu truth; definitive rejection becomes failed; transport ambiguity remains unknown. Neither the Host nor Client automatically retries an ambiguous provider write.
- Task-list discovery, reads, reconciliation, references, and writes resolve credentials afresh and re-prove the pinned actor identity before touching a task resource. Credential values, bearer tokens, raw provider bodies/errors, task text, member IDs, comments, and canonical URLs never enter generic audit/Activity/Outbox payloads or logs.
- The authorized browser displays the binding, sync health, hierarchical tasks, assignees, followers, comments, completion, canonical links, and non-delivered effect state. It uses the Connection Center's explicit verified route fences for binding, keeps no browser authority, preserves safe same-Project state across reconnect, and clears it on Project switch, logout, expiry, Owner change, and Fiber disposal.

## T09 Feishu task workflow invariants

- The Owner defines one closed workflow schema with 2–100 stable logical state IDs, bounded unique display names/colors, one initial state, explicit allowed transitions, and one or more terminal states with no outgoing transition. Display-name or color changes never replace logical identity.
- One Project workflow maps to one `single_select` field on its immutable primary task-list binding. The field GUID and complete `stateId -> optionGuid` mapping are stable provider identities; configuration versions are append-only and the mutable head advances under both Project task and workflow CAS.
- Feishu custom-field values remain authoritative. Workbench transition rules constrain only Workbench-originated writes; a Feishu-originated state still converges through event or complete reconciliation. An unknown option GUID remains visible as an unrecognized, blocked compatibility fact instead of being guessed or discarded.
- Create, existing mapping, and migration all inspect the exact pinned route and task list. Missing/wrong-type fields, missing/hidden/duplicate options, unmapped task values, and removal or hiding of an in-use state block configuration before provider mutation. A newly created option is committed only with the GUID returned by Feishu.
- The field `updated_at` token is an opaque observation. The provider PATCH has no atomic expected-version input, so GET-before-PATCH and response validation are conflict detection, not a claim of provider-enforced CAS; an observed field-version conflict fails closed and requires a fresh preview.
- Custom-field create/PATCH has no documented provider idempotency token. Before either write, Workbench durably reserves a normalized workflow operation with receipt, redacted Outbox intent, and hash-chained audit. One claim permits one provider attempt. Recovered inflight or transport-ambiguous work becomes `unknown`, is never automatically redelivered, and requires explicit field reconciliation or Owner resolution.
- A Workbench task status write carries Project task revision, opaque task remote version, workflow revision, current mapped value, requested logical state, and one caller-stable command identity. Reservation validates the allowed edge and freezes the exact field/option GUID patch before one-attempt delivery.
- A terminal state only derives `terminal-state-awaiting-owner-confirmation`. It never writes Feishu `completed_at`; authoritative completion remains a separate explicit Owner task command.
- Field/option names, task values, raw provider bodies/errors, resource identifiers, and credentials stay out of generic audit, Activity, Outbox payloads, and logs. Authorized Project Tasks projections may return the bounded business mapping and compatibility facts.

## T10 Feishu calendar and Milestone invariants

- A Project has zero or one immutable primary Feishu Calendar v4 binding. Binding selects an accessible calendar or creates one shared calendar, pins the exact verified Bot/User route generation and actor binding, and never falls back to the other identity. A selectable calendar is not deleted or third-party, has type `primary` or `shared`, and grants the pinned actor `writer` or `owner`; one provider calendar cannot silently become another local Project's primary binding.
- Workbench owns Milestone identity, bounded name/description, creation provenance, and the immutable event binding. Feishu owns the formal start/end date and remote event status. One provider event cannot back two local Milestones, and T10 binds only non-recurring, non-exception events organized by the bound calendar.
- Formal dates use one closed value: either strict ISO all-day start plus exclusive end dates, or offset-bearing RFC 3339 timed instants plus one validated IANA timezone. Both ends have the same kind and `start < end`. The Feishu response, not the submitted request, becomes the authoritative projection.
- Calendar v4 exposes no event resource version, ETag, update timestamp, conditional PATCH, or equivalent provider CAS. `remoteObservationVersion` is a versioned SHA-256 digest of the canonical Feishu authority tuple (calendar/event/organizer identity, status, recurrence, start, and end). It is an opaque comparison token, not a claim of provider-enforced atomicity.
- A Workbench date write carries Project schedule revision, Milestone revision, remote observation version, one caller-stable command identity, causation ID, and closed reason. The Host re-proves the pinned identity and GETs the event before reservation. A changed observation fails closed, commits the fresh Feishu dates as authority, and performs no PATCH. A matching observation permits one exact start/end PATCH followed by response validation; a race can still be discovered by the response or later reconciliation.
- Event creation sends Feishu's documented application-and-calendar-scoped `idempotency_key`, derived from the immutable local operation identity. Calendar creation and Event PATCH have no documented provider idempotency token. Every external write is durably reserved with accepted receipt, redacted Outbox intent, and hash-chained audit before one claim and one provider attempt. Ambiguous or restart-recovered inflight work becomes `unknown` and is never automatically redelivered.
- A trusted calendar-change notification is only a hint. Event ID/change type are gray-release provider fields and cannot be required. The Inbox deduplicates the notification envelope and triggers bounded GET reconciliation for every event bound to that Project; periodic reconciliation repairs missing/reordered notifications and drains on disposal.
- Every authoritative schedule/status change atomically advances one Project schedule revision and appends one `ProjectScheduleChange` with source, changed-field codes, and object revisions. This durable change feed is the dependency-consumer seam for later planning/risk modules. Authorized Milestone projections may show bounded dates, event links, sync status, effects, and recent changes; generic Activity/audit surfaces remain redacted.
- Calendar/event titles, descriptions, exact dates, resource IDs/links, raw provider bodies/errors, credentials, tokens, and identity values stay out of generic audit, Activity, Outbox payloads, receipts, logs, and diagnostics.
- The Client exposes localized accessible calendar discovery/binding, existing/create event Milestone flows, all-day/timed input, explicit date-change confirmation, canonical event links, sync health, recent changes, exact ambiguous-browser retry, and unknown/conflict recovery. Project switch, logout, expiry, Owner change, selection clearing, HMR, and Fiber disposal clear protected drafts and discovery results.

## T11 Deliverable planning and acceptance invariants

- A Deliverable is one Workbench-owned executable object with an immutable plan: bounded name/description, 1–20 ordered Acceptance Criteria with Host-derived IDs, exactly one active Accountable, distinct active Contributors, a Human Sponsor under the T05 rule, one designated active Human Acceptor, and 1–50 distinct task GUIDs currently visible in the Project's Feishu-authoritative task projection.
- The designated Acceptor is a responsibility assignment, not a browser identity. V1's authenticated Owner records every formal acceptance decision; the immutable request and decision retain the designated Acceptor separately, and neither Host nor Client claims that ProjectMember signed in. T11 does not implement External Attestation.
- A Deliverable binds exactly one event in the Project's immutable Calendar binding through the existing-event or create-event path. The complete authoritative `ProjectCalendarSchedule`, remote status, event link, and observation version remain Feishu-owned facts. One internal closed Calendar Commitment seam enforces that the same calendar/event pair cannot back both a Milestone and a Deliverable; Schema v9→v10 backfills every T10 Milestone before applying that uniqueness rule.
- Deliverable task links are stable GUID references only. Reads join the current T08 projection and expose each link as available or unavailable; T11 never creates, updates, completes, or copies authority from a Feishu task. A Deliverable cannot enter review unless at least one linked task remains visible.
- A candidate artifact is an immutable declared exact-version reference with source (`managed`, `local`, or `feishu`), resource ID, required version ID, display name, optional HTTPS canonical URL, optional SHA-256 content digest, and a Host-derived reference digest. T11 has no File adapter and never upgrades declared provenance into verified existence, readability, or permission.
- Each acceptance request freezes one complete Deliverable revision: plan, responsibility, calendar observation, task GUIDs, and 1–20 distinct candidate version references. At most one request is pending. Calendar authority movement advances the Deliverable revision and makes a pending request effectively stale; stale cannot be approved but may be rejected or returned for changes.
- Every acceptance decision has mandatory feedback and exactly one `met | not-met` result for every frozen criterion. Approval requires all criteria met; needs-changes requires at least one not-met result. Rejected and needs-changes requests remain immutable and return the Deliverable to planned for a new round.
- Approval atomically appends the Owner decision, marks the request and Deliverable accepted, and creates one immutable Final Release containing exactly the complete candidate set frozen by that request. The decision command cannot replace, add, or omit artifacts; Final Release and version rows are append-only and cannot be reopened or repointed in T11.
- Acceptance decisions require both `workbench.review.decide` and `workbench.project.deliverable.accept`, resolved to the identical Owner/organization/team scope before persistence. All four Deliverable behaviors retain receipt-first replay, exact revision fences, cancellation, atomic audit/Outbox/receipt facts, and detached post-commit publication.
- Names, descriptions, criteria, responsibility member IDs, task GUIDs, calendar identifiers/dates/links, artifact identifiers/versions/digests, criterion outcomes, and feedback never enter generic audit, Activity, Outbox payloads, receipts, logs, or diagnostics. The separately authorized Deliverable Activity feed references immutable plan/request/decision snapshots and matching audit IDs so the responsibility and acceptance chain remains replayable.
- The localized Client uses native labeled forms, progressive disclosure for existing/timed event paths, compact Deliverable cards, textual state/error feedback, exact ambiguous retry, responsive no-overflow layout, and complete protected-draft cleanup on Project switch, logout, expiry, Owner change, selection clearing, HMR, and Fiber disposal.

## Ticket boundary
